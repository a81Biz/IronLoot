# E-022 — Un error del cliente sale como fallo del servidor en el depósito

## Cómo apareció

No se buscaba. Salió al ejecutar por primera vez la suite e2e completa (PT-128), contra el stack
real: Postgres con esquema aplicado por migraciones, Redis y Mailhog en marcha.

De los 42 fallos, 41 son `400` por specs viejos. **Este es el único `500`**, y por eso se miró.

## Lo observado

`wallet.e2e-spec.ts:75-81` — un depósito con una referencia inventada:

```
POST /wallet/deposit
{ "amount": 100, "referenceId": "PAY-100" }

esperado 201 "Created", recibido 500 "Internal Server Error"
```

El log de la aplicación, en la misma petición:

```json
{"level":"error","message":"PayPal request to
 https://api-m.sandbox.paypal.com/v2/checkout/orders/PAY-100 failed with status 404"}
```

## La cadena, leída en el código

```
wallet.controller.ts:102     const payment = await this.paymentsService.verifyPayment(dto.referenceId);
        ↓
payments.service.ts:199      else if (referenceId.startsWith('PAY-')) {
                               result = await this.paypalProvider.verifyPayment(referenceId);
        ↓
paypal.provider.ts:383-387   const order = await this.authorizedFetch<PaypalOrder>(
                               `${this.apiBaseUrl}/v2/checkout/orders/${externalId}`, ...);
                             ← SIN try/catch. PayPal devuelve 404 y esto LANZA.
        ↓
                             La excepcion sube sin mapear -> HTTP 500
```

`verifyPayment` **sí** contempla el caso de prefijo desconocido —lanza `BadRequestException('Invalid
or unsupported payment reference')`, `payments.service.ts:221`—. Pero un prefijo **conocido** con un
identificador que la pasarela no encuentra no pasa por ahí: revienta dentro del adaptador.

## Por qué importa, más allá del código de estado

1. **Semántica**: una entrada inválida del cliente es 4xx. Devolver 5xx dice «el servidor está
   roto» cuando el servidor está bien.
2. **Contamina las señales de fiabilidad**: `error_events` y cualquier alerta basada en 5xx
   registran fallos de servidor causados por entrada del cliente. Afecta a lo que D3 y D5 miden.
3. **Fuga menor de información**: el mensaje nombra la URL del entorno de PayPal y la referencia.
4. **Es un defecto ya conocido en esta casa.** PT-124 / F-41 se tituló literalmente *«un error del
   cliente no se registra como fallo del servidor»*. Se corrigió en la subida de ficheros y
   sobrevive en el depósito.

## Dónde ocurre

`POST /api/v1/wallet/deposit` — la ruta de depósito de **P-005 WalletTransaction**, producto
**CRÍTICO**. Exige sesión (`JwtAuthGuard`) y está limitada a 10 peticiones/minuto
(`@Throttle`, `wallet.controller.ts:90`).

## Lo que esta evidencia NO demuestra

- **No se reprodujo con un usuario real por HTTP fuera de la suite**: la observación viene de la
  corrida e2e, que es una petición real a través de la pila completa, pero con credenciales de
  sandbox de PayPal.
- **No se comprobó el comportamiento con credenciales de producción.** Con credenciales válidas y
  una orden inexistente, PayPal devolvería igualmente 404 y la cadena sería la misma — pero eso es
  razonamiento, no medición.
- **No se revisaron los otros adaptadores** (Mercado Pago, Stripe) para ver si tienen el mismo
  hueco. Es lo primero que debería mirar el PT que corrija esto.
- No se intentó ninguna explotación.
