# E-017 — Las 23 migraciones no reproducen el esquema que la auditoría certificó

## Por qué se capturó

`[R70]` prohíbe aceptar las migraciones como verdad del esquema. Se comprobó lo contrario de lo
habitual: **si el esquema real puede reconstruirse desde las migraciones**, que es lo único que un
despliegue tiene.

## 1. La base real no tiene historial de migraciones

```
$ docker exec ironloot-api sh -c 'cd /app && npx prisma migrate status'
23 migrations found in prisma/migrations
Following migrations have not yet been applied:
20260106100011_init_auctions_module
… (las 23)

$ docker exec ironloot-db psql -U ironloot -d ironloot_db -c "\dt _prisma*"
Did not find any relation named "_prisma*".
```

Las 33 tablas existen y el esquema coincide con `schema.prisma`:

```
$ npx prisma migrate diff --from-schema-datamodel prisma/schema.prisma \
                          --to-schema-datasource prisma/schema.prisma
No difference detected.
```

**El esquema real es correcto y ninguna migración lo construyó.**

## 2. Quién lo construye

`src/api/scripts/entrypoint.dev.sh:52`

```bash
npx prisma db push --accept-data-loss 2>&1 || {
  echo "⚠️ db push failed, trying migrate deploy..."
  npx prisma migrate deploy 2>&1 || echo "⚠️ migrate también falló"
}
```

`db push` no escribe `_prisma_migrations`. Por eso el historial no existe: **las migraciones no se
han ejecutado nunca en este entorno**, y el respaldo de la línea 54 tampoco puede ejecutarse, porque
`migrate deploy` sobre una base construida con `db push` devuelve `P3005 — The database schema is
not empty` (observado más abajo).

## 3. Qué producen las migraciones

Base sombra limpia, las 23 aplicadas en orden:

```
$ docker exec ironloot-db psql -U ironloot -d postgres -c "CREATE DATABASE ptsa_shadow"
$ DATABASE_URL=…/ptsa_shadow npx prisma migrate deploy
All migrations have been successfully applied.
```

Diferencia contra `schema.prisma`:

```
[+] Added enums          PaymentMethodType · AccountVerificationStatus
[+] Added tables         account_verifications
[*] NotificationType     [+] variante AUCTION_SOLD
[*] payment_cycles       [+] columna provider_ref
[*] payments             [-] índice sobre (reference)
                         [+] índice ÚNICO sobre (reference)
[*] user_payment_methods [+] columnas type · card_last4 · paypal_email
```

Comparación directa de tablas — real contra migraciones:

```
$ diff <(tablas ironloot_db) <(tablas ptsa_shadow)
< account_verifications        # sólo en la real
```

Índices de `payments` en la base que producen las migraciones:

```
payments_pkey            UNIQUE (id)
idx_payments_reference   btree (reference)      ← NO es único
```

En la base real:

```
payments_reference_key   UNIQUE (reference)
```

## 4. Qué hace la aplicación contra esa base

Cliente Prisma generado desde `schema.prisma`, apuntando a la base de las migraciones:

```
  FALLA  userPaymentMethod.findMany -> The column `user_payment_methods.type` does not exist
  FALLA  paymentCycle.findMany      -> The column `payment_cycles.provider_ref` does not exist
  FALLA  accountVerification.findMany -> The table `public.account_verifications` does not exist
  OK     payment.findMany
```

**Tres de cuatro sondas fallan**, y una de ellas es `payment_cycles`: el ciclo de pago de PT-080,
núcleo de P-004.

## Lectura

Dos hechos separados, ambos observados:

1. **El artefacto desplegable no reproduce el sistema auditado.** Lo que se certificó es la base que
   `db push` construye en desarrollo. Las migraciones producen otra cosa, y sobre esa otra cosa la
   aplicación no arranca sus consultas.
2. **`payments.reference` pierde la unicidad.** CLAUDE.md declara esa unicidad como la garantía de
   que un reintento de acreditación no duplica el asiento. En la base de las migraciones esa
   garantía no existe. No se probó una acreditación doble —la aplicación falla antes, por las
   columnas que faltan—, así que esto se registra como pérdida de una restricción declarada, no
   como duplicado observado.

## Lo que esta evidencia NO demuestra

- No demuestra que exista un despliegue productivo afectado: **no hay ninguno**. El `Dockerfile` de
  producción termina en `CMD ["node", "dist/main"]` y no aplica esquema alguno; `ci.yml` no tiene
  job de despliegue. El daño es potencial y se materializa al reconstruir cualquier entorno desde
  las migraciones.
- No se midió qué migración concreta introdujo cada divergencia.

## Limpieza

`ptsa_shadow` se eliminó al cerrar la sesión. No se tocó `ironloot_db`.
