# E-024 — El portal pide una ruta de ajustes que el API no tiene

## Cómo apareció

Verificando la ruta de `settings` a raíz de H-019, y **después** de consultar `docs-v2/` como manda
FDGE. Comparando lo que el CLIENT pide contra lo que el API expone.

## Lo que pide el CLIENT

`src/apps/client/src/app.controller.ts:85-88`

```ts
@Get("/settings")
@Render("pages/settings.html")
async settings(@Req() req) {
  const settings = await apiGet(getToken(req), "/api/v1/users/settings");
```

Y la página está en el menú principal del portal: `views/layouts/client.html:57` →
`<a href="/settings">Configuración</a>`.

## Lo que expone el API

`src/api/src/modules/users/users.controller.ts`

```
177:  @Get('me/settings')
190:  @Patch('me/settings')
```

**No hay `@Get('settings')`.**

## Lo medido, con sesión real

Usuario registrado por la vía pública, verificado en base, sesión iniciada:

```
400  GET /api/v1/users/settings
     {"code":"VALIDATION_ERROR","message":"Validation failed (uuid is expected)"}

200  GET /api/v1/users/me/settings
     {"language":"es","notifications":{"email":true,"inApp":true}}
```

## Por qué el error engaña

La petición no cae en un 404: cae en el comodín `@Get(':id')` del mismo controlador. El
`ParseUUIDPipe` recibe la cadena `settings` como identificador, la rechaza, y devuelve **400 —
uuid inválido**.

Un 404 habría dicho «esa ruta no existe». El 400 dice «el identificador está mal», que manda a
quien lo investigue a mirar el identificador. **No es que el error falte: es que apunta al sitio
equivocado.**

## Lo que esta evidencia NO cubre

- **No se han barrido las demás llamadas del CLIENT al API.** Puede haber más rutas inexistentes;
  no se ha medido. Es lo primero que debería hacer el PT que corrija esto.
- No se ha determinado desde cuándo está roto.
- No se ha comprobado el ADMIN ni el BASE.
