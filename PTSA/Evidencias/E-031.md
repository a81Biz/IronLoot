# E-031 — La salud, leída en vivo

F8 exige **leer**, no dar por hecho que la observabilidad funciona.

## El registro funciona

```
request_logs en las últimas 24 h: 545
silent_failure_count = 25  (== línea base; sin silencios nuevos tras 25 PT)
```

## El endpoint básico está sano

```json
GET /api/v1/health  → 200
{"status":"healthy","version":"0.5.1","environment":"development","uptime":1307}
```

Es el que usan los `healthcheck` de `docker-compose` (`docker-compose.yml:192`, ruta con el prefijo
global — la corrección de H-017). Los cinco contenedores están `healthy`.

## El endpoint detallado dice «degraded», y lo dirá siempre

```json
GET /api/v1/health/detailed
{
  "status": "degraded",
  "dependencies": {
    "database": { "status": "up", "latency": 0 },
    "redis":    { "status": "unknown", "message": "Redis check not implemented" }
  }
}
```

Leído en el código, son dos líneas:

```ts
// health.service.ts:89
return { status: 'unknown', message: 'Redis check not implemented' };

// health.service.ts:65
status: anyDown ? 'unhealthy' : allUp ? 'healthy' : 'degraded',
```

`redis` **nunca** puede valer `up`, así que `allUp` **nunca** es cierto y el endpoint **nunca** puede
devolver `healthy`. Dos consecuencias, y la segunda es la que importa:

1. **Reporta un problema que no existe, en cada consulta.** Es ruido que enseña a descartar la fuente —
   el mismo mecanismo que PT-159, PT-166 y PT-172 vinieron a quitar de la suite.
2. **Y si Redis se cayera de verdad, diría exactamente lo mismo.** `unknown` → `degraded`, igual que
   ahora. **Una caída real de Redis es indistinguible del funcionamiento normal** en el único endpoint
   que existe para diagnosticarla.

### Por qué eso pesa en este sistema y no es cosmético

`REDIS_URL` es el **único contrato de Redis** (PT-137) y lo usan **las colas, el rate limiting, el
cerrojo distribuido y las sesiones de ADMIN**. RULE-17 llegó a exigir que el proceso **aborte** si falta,
precisamente porque un Redis mal configurado producía *«Nest application successfully started»* seguido
de un 500 que **no menciona Redis**.

El arranque, entonces, está protegido. Lo que no está cubierto es **la degradación en caliente**: Redis
se cae con el proceso ya en marcha, y el endpoint de diagnóstico no lo puede decir. → **H-026**

## Lo que sí está bien y conviene no confundir

- El `healthcheck` de Docker apunta a `/api/v1/health`, que devuelve 200. **Nada depende del endpoint
  roto**: no hay contenedores cayéndose por esto.
- `database` **sí** se comprueba de verdad, con latencia medida.
- La distinción es exactamente esa: el sistema está sano; lo que no se puede **observar** es Redis. Por
  eso el hallazgo es D3 (Observabilidad y Recuperación) y no D2.
