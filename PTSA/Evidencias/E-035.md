# E-035 — Los tres cierres, comprobados ejecutando

## H-029 — el guard rechaza lo que antes dejaba pasar

```
El guard de reCAPTCHA falla cerrado — H-029 (PT-182)
  ✓ C1: desactivado, pasa sin mirar nada — no cambia el comportamiento por defecto
  ✓ C2: activado y SIN token, sigue rechazando
  ✓ C3: activado con un token BASURA, ya NO pasa — es el defecto
  ✓ C4: activado con un token que Google valida, pasa
  ✓ C5: activado SIN secreto, rechaza — no pasa por defecto
    ✓ AC-01: si Google no responde, NO se deja pasar
    ✓ AC-02: el token tambien se acepta en el cuerpo, como antes
```

**C3 es el defecto** y **AC-01 es el defecto por la puerta de al lado**: un timeout no puede ser una puerta,
porque lo provoca cualquiera que sepa provocarlo. C1 y AC-02 son los casos de control — el arreglo no cambia
el comportamiento por defecto ni la forma de mandar el token.

## H-030 — el reenvío produce un correo real

Guarda:

```
El reenvio de verificacion envia de verdad — H-030 (PT-182)
  ✓ C1: se llama al servicio de correo con el destinatario y el token
  ✓ C2: si el envio FALLA, no se responde exito
    ✓ AC-01: un correo ya verificado no reenvia nada
    ✓ AC-02: un usuario que no existe no reenvia nada
```

Y en vivo, contra Mailhog, que es lo que de verdad lo demuestra —**la respuesta ya decía «enviado» cuando no
enviaba nada, así que la respuesta no es evidencia de nada**:

```
registro               HTTP 201
correos tras registro  1  ['Verifica tu cuenta de Iron Loot']
reenvio                HTTP 200  {'message': 'Verification email sent. Please check your inbox.'}
correos tras reenvio   2  ['Verifica tu cuenta de Iron Loot', 'Verifica tu cuenta de Iron Loot']

OK — el reenvio produjo un correo real (1 -> 2)
```

**Lo que se afirma es la diferencia `1 → 2`**, no el `HTTP 200`.

C2 merece una nota: el envío **no se envuelve en `catch`** a propósito. Un `catch` que se comiera el fallo
reproduciría el defecto por otra vía — el usuario volvería a leer «revisa tu bandeja» sin que nada haya
salido.

Y el arranque real, porque inyectar una dependencia nueva puede romper el grafo de módulos y eso no lo dice
una prueba unitaria:

```
Nest application successfully started
GET /api/v1/health → 200
```

## H-031 — la reserva ya no es el valor desprotegido

```
  ✓ C3: el corte por confirmación son 72 h por defecto
  ✓ C7: la reserva de `docker-compose` NO es el valor desprotegido
    ✓ AC-01: `SETTLEMENT_HOLDBACK_HOURS=0` libera en el primer tic
```

**C7 se vio fallar**, que es lo único que lo convierte en un control. Con la reserva devuelta a `:-0`:

```
  ✕ C7: la reserva de `docker-compose` NO es el valor desprotegido
  Tests: 1 failed, 9 passed, 10 total
```

Y C7 mira el `docker-compose.yml`, **no el servicio**, a propósito: el servicio ya tenía su reserva de 72
(C3) y **nadie la vio fallar nunca**, porque el compose siempre le pasaba un valor. La guarda vivía apuntando
al sitio donde el agujero no estaba.

QA sigue funcionando porque ahora **declara** su `0` en el `.env` en vez de heredarlo: es configurar, no
falsear.

## Lo que esta evidencia NO sostiene

- **Que reCAPTCHA esté protegiendo el registro hoy.** No lo está: `RECAPTCHA_ENABLED=false`. Sostiene que el
  día que se encienda, protegerá — y que si se enciende a medias, **rechaza** en vez de aparentar.
- **Que no queden controles decorativos.** Sostiene que estos tres ya no lo son. El barrido que los encontró
  miró guards, `TODO` vivos y valores por defecto; hay más sitios donde una afirmación puede no cumplirse.
