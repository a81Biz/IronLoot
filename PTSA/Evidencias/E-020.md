# E-020 — La documentación de arquitectura quedó en NestJS 10; el código está en 11

## Lo que dicen los documentos que el alcance declara auditables

`docs/enterprise-documentation/03-TRD.md:13`

```
| NestJS | ^10.3.0 | `src/api/package.json:36` |
```

`docs/enterprise-documentation/06-Backend-Architecture.md:9-13`

```
├── api/           — Main REST API + WebSocket server (NestJS 10, port 3000)
│   ├── base/      — Public SSR site (NestJS 10, port 5174)
│   └── client/    — Private SSR portal (NestJS 10, port 5175)
├── admin/         — Admin backoffice (NestJS 10, port 3001)
```

## Lo que dice el código

```
  src/api              @nestjs/core=^11.0.0
  src/admin            @nestjs/core=^11.0.0
  src/apps/base        @nestjs/core=^11.0.0
  src/apps/client      @nestjs/core=^11.0.0
```

PT-126 (`6d6864d`, `6d1b4ef`, 2026-07-27) subió los cuatro servicios a NestJS 11 y Express 5. La
documentación no se tocó.

## Por qué esto es peor que un número viejo

La fila del TRD **cita su fuente**: `src/api/package.json:36`. Un lector que confíe en la cita lee
un dato falso avalado por una referencia concreta. Es el mismo mecanismo que CLAUDE.md ya describe
para la deuda técnica: *«cerrar una deuda técnica son dos escrituras… el registro llegó a mentir dos
veces»*. Aquí la segunda escritura tampoco ocurrió, y el registro afectado está **dentro del alcance
declarado de auditoría** (`audit-scope.yaml`, sección `docs`).

## Alcance de la comprobación

Se verificó la afirmación de versión de framework en los dos documentos citados. **No se hizo una
revisión documental exhaustiva** de los cinco documentos del alcance. Otras afirmaciones podrían
estar igualmente desactualizadas y no se han medido.

## Lo que sí se comprobó y era correcto

- `CLAUDE.md`: «CORE — 8 suites / 134 tests» → ejecutado: 8 suites, 134 tests. Exacto.
- `CLAUDE.md`: puertos 3000 / 3001 / 5174 / 5175 → coinciden con los contenedores en marcha.
- `CLAUDE.md`: «27 feature modules» → `ls src/api/src/modules | wc -l` = 27. Exacto.

## Revisión — S-002 (2026-07-27): dos correcciones y un alcance mucho mayor

Revisión abierta a raíz de una objeción del humano: *«no puede ser que la migración no esté
documentada. Se migró NestJS 11.1.28 / Express 5.2.1 y debería estar documentado»*.

**Tenía razón en lo que señalaba, y esta evidencia estaba mal redactada.**

### Corrección 1 — La migración SÍ está documentada, y bien

PT-126 dejó registro en los cuatro artefactos que le corresponden por FDGE:

| Artefacto | Contenido |
|---|---|
| `docs/implementation/REFACTOR_SCOPE.md` | STATE 1-R completo — la variante correcta para un REFACTOR. Alcance, qué cambia, autorización humana citada literalmente |
| `docs/implementation/CONTEXT_ANALYSIS.md` | Análisis arquitectónico |
| `docs/implementation/HISTORY.log` | Entrada detallada: los cuatro servicios, `path-to-regexp` 3→8, `body-parser` 1→2, y los cuatro defectos latentes que destapó la migración (`JWT_SECRET`, `JWT_ACCESS_EXPIRY`, el adaptador de Handlebars, F-42) |
| `docs/implementation/HANDOFF.md` | Estado |

**El hallazgo nunca fue sobre eso.** E-020 se redactó de forma que podía leerse como «la migración
no se documentó», y no es lo que se midió. Lo que se midió es que **la documentación de
arquitectura** —`docs/enterprise-documentation/`, corpus distinto de `docs/implementation/`— no se
actualizó. Son dos corpus con dueños distintos:

```
docs/implementation/          FDGE — el registro del trabajo         ✅ actualizado por PT-126
docs/enterprise-documentation/  Foundation Protocol — la referencia   ❌ sigue en NestJS 10
```

### Corrección 2 — Las versiones exactas

E-020 citaba `^11.0.0`, que es el **rango declarado** en `package.json`. La **versión resuelta**,
leída del contenedor en marcha, es la que dio el humano:

```
$ docker exec ironloot-api node -p "require('@nestjs/core/package.json').version"
11.1.28
$ ... require('express/package.json').version
5.2.1
```

Ambas cifras se incorporan. Rango y versión resuelta son datos distintos y los dos importan.
