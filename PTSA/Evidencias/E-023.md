# E-023 — Un `PATCH` parcial de ajustes destruye los ajustes que no envías

## Cómo apareció

Al corregir los specs e2e de PT-131, `settings.e2e-spec.ts` seguía fallando después de arreglar
todas las capas de contrato viejo. El test afirmaba algo razonable —que cambiar el idioma no debe
tocar las notificaciones— y el producto no lo cumplía.

**El test tenía razón.** Se comprobó contra el sistema en marcha, no contra el spec.

## Lo observado

Usuario recién registrado por la vía pública, verificado, con sesión real:

```
ANTES   GET  /api/v1/users/me/settings
        {"language": "es", "notifications": {"email": true, "inApp": true}}

        PATCH /api/v1/users/me/settings   {"language": "en"}
        respuesta: {"language": "en"}

DESPUES GET  /api/v1/users/me/settings
        {"language": "en"}
```

**`notifications` ha desaparecido.** No se envió, no se pidió borrarlo, y se borró.

## La causa, leída en el código

`users.service.ts:493` llama a `deepMerge(currentSettings, dto)`, y `deepMerge` recorre
`Object.keys(source)` (línea 527).

El `dto` **no es un objeto plano**: es una instancia de `UserSettingsDto` creada por
`plainToInstance`, porque `main.ts:84` configura el `ValidationPipe` con `transform: true`. Esa
instancia lleva **todas las propiedades declaradas como claves propias**, incluidas las que no
venían en la petición, con valor `undefined`.

Así que para `{"language":"en"}`:

```
Object.keys(source)  ->  ['language', 'notifications']
                                        ↑ presente, con valor undefined

notifications:  isObject(undefined) === false  ->  output.notifications = undefined
```

`deepMerge` existe **precisamente** para no hacer esto. Funciona bien; lo que le llega ya está mal.

## Por qué importa

El contrato de un `PATCH` es «cambia lo que te mando y deja lo demás». Aquí es lo contrario, **y en
silencio**: la petición devuelve 200 y el usuario no se entera de que ha perdido sus preferencias de
notificación hasta que deja de recibir avisos.

Y `notifications` gobierna si el usuario recibe correos y avisos in-app. En una plataforma de
subastas, perder eso significa perderse que te han superado la puja.

## Lo que esta evidencia NO demuestra

- **No se ha revisado si otros endpoints `PATCH` tienen el mismo patrón.** Es lo primero que
  debería mirar quien lo corrija: cualquier servicio que mezcle un DTO transformado contra un JSON
  almacenado tiene el mismo agujero.
- No se ha medido cuántos usuarios reales han perdido ajustes: la base de desarrollo tiene 4
  usuarios y no es representativa.
- No se intentó explotarlo ni se buscó una vía de escalada.
