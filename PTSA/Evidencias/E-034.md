# E-034 — Tres controles que aparentan estar puestos

El barrido no buscó errores: buscó **afirmaciones**. Un `return true` bajo un nombre que promete verificar,
una respuesta que dice «enviado», una variable que declara una espera. Los tres decían algo que el código no
hacía, y **ninguno fallaba**: por eso llevaban meses ahí.

## H-029 — El guard de reCAPTCHA

`src/api/src/modules/auth/guards/recaptcha.guard.ts`, tal como estaba:

```ts
if (!token) throw new ForbiddenException('CAPTCHA token required');
// TODO: Verify token with Google API
return true; // Mock success for now
```

Comprobaba que el token **existiera**, nunca que fuese válido. Con `RECAPTCHA_ENABLED=true`, la cadena `"x"`
pasaba igual que un token legítimo. Protege **`POST /auth/register`**.

No había exposición mientras la variable estuviera en `false` —su valor por defecto—, y **ahí estaba el
peligro**: el día que alguien la encendiera, creería tener protección contra bots y no la tendría. Es la
familia de H-004 (la validación del método de pago comentada en el retiro).

## H-030 — El reenvío de verificación

`src/api/src/modules/users/users.service.ts`, tal como estaba:

```ts
// TODO: Send actual email when NotificationsModule is ready
// await this.emailService.sendVerificationEmail(user.email, emailVerificationToken);

return { message: 'Verification email sent. Please check your inbox.' };
```

Generaba el token, lo guardaba, escribía el apunte de auditoría **y no enviaba nada**. La respuesta decía
que sí.

Dos cosas lo hacen ALTA y no MEDIA:

1. **Es el camino de recuperación** de una cuenta que no se puede activar. Lo pide exactamente quien no
   recibió el correo del registro, y se le dejaba esperando para siempre.
2. **La condición del `TODO` ya se cumplía.** `notifications/email.service.ts:24` implementa
   `sendVerificationEmail(to, token)` y está en uso en el registro. El comentario sobrevivió al trabajo que
   lo habilitaba — F-33 otra vez.

## H-031 — La reserva del holdback

`docker-compose.yml`, tal como estaba:

```yaml
- SETTLEMENT_HOLDBACK_HOURS=${SETTLEMENT_HOLDBACK_HOURS:-0}
```

La espera que protege al comprador **valía cero por defecto**. Un despliegue que no declarase la variable
liberaba el neto de la venta al instante de la confirmación, sin ventana, y nada lo habría dicho: el cron
corre, los asientos cuadran, la espera simplemente no existe.

Es mío y de hoy: lo introdujo **PT-174** hace unas horas para que la fase 35 de QA no esperase tres días. La
conveniencia de QA se colocó donde vive el valor por defecto de producción.

## Lo que esta evidencia NO sostiene

- **Que H-029 fuera explotable hoy.** No lo era: la variable está en `false`. Sostiene que el control no
  existía el día que se encendiera.
- **Que H-031 llegara a producción.** No llegó: nació y murió el mismo día. Se registra porque **la
  exposición era real** y esconderla en prosa la haría invisible al recuento.
