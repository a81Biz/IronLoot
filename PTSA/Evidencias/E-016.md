# E-016 — El API sirve `/uploads` con el Content-Type que dicta la extension del fichero

## Qué se ejecutó

Se escribieron tres ficheros en el directorio que sirve `ServeStaticModule`, dentro del contenedor
en ejecución, y se pidió cada uno por HTTP. **No se explotó nada**: se midió qué cabecera devuelve
el servidor según la extensión.

```
docker exec ironloot-api sh -c 'printf "<script>alert(1)</script>" > /app/uploads/ptsa-prueba.html'
curl -D- -o /dev/null http://localhost:3000/uploads/ptsa-prueba.html
```

## Salida observada

```
  .html  -> HTTP/1.1 200 OK  X-Content-Type-Options: nosniff  Content-Type: text/html; charset=UTF-8
  .svg   -> HTTP/1.1 200 OK  X-Content-Type-Options: nosniff  Content-Type: image/svg+xml
  .png   -> HTTP/1.1 200 OK  X-Content-Type-Options: nosniff  Content-Type: image/png
```

Los tres ficheros de prueba se borraron acto seguido; el directorio quedó en 0 ficheros.

## Lectura

**`nosniff` no protege aquí, y esa es la parte que engaña.** `X-Content-Type-Options: nosniff` impide
que el navegador *adivine* un tipo distinto del declarado. Aquí el tipo declarado **ya es**
`text/html`: no hay nada que adivinar. La cabecera está haciendo su trabajo y aun así el fichero se
ejecuta.

## La otra mitad de la cadena (lectura de código, no ejecución)

`upload.service.ts:19`:

```ts
const fileName = `${uuidv4()}${extname(file.originalname)}`;
```

`file.originalname` es **el nombre que envía el cliente** en la cabecera del `multipart`. La
extensión con la que el fichero se guarda —y por tanto la que decide el `Content-Type` medido
arriba— la elige quien sube.

`upload.controller.ts:53` sí valida el tipo, pero valida `file.mimetype`, que es **también** un campo
del `multipart` que escribe el cliente. Ninguna de las dos comprobaciones mira el contenido.

## Alcance de la sesión: las cookies llegan a este origen

`.env:118` → `COOKIE_DOMAIN=.ironloot.local`. El punto inicial hace que la cookie de sesión se envíe
a **todos** los subdominios, `api.ironloot.local` incluido. Un script ejecutándose en el origen del
API está dentro del alcance de la cookie.

## Lo que esta evidencia NO demuestra

No se subió un fichero por el endpoint real: eso exige una sesión, y la prueba no la necesitaba
—las dos mitades de la cadena se miden por separado y ambas están verificadas—. Queda como
verificación pendiente en la evidencia post-corrección.
