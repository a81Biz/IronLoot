# H-018 — El depósito devuelve 500 cuando la referencia de pago no existe

## Descripción

`POST /api/v1/wallet/deposit` con un `referenceId` desconocido que empiece por `PAY-` devuelve
**500 Internal Server Error**. El adaptador de PayPal consulta la orden, PayPal responde 404, el
adaptador lanza, **nadie lo captura**, y la excepción sube sin mapear.

```
POST /wallet/deposit  { "referenceId": "PAY-100" }   ->  500

log: PayPal request to .../v2/checkout/orders/PAY-100 failed with status 404
```

`paypal.provider.ts:383-387` llama a `authorizedFetch` sin `try/catch`.

`verifyPayment` **sí** contempla el prefijo desconocido (`BadRequestException`,
`payments.service.ts:221`). Lo que no contempla es un prefijo **conocido** con un identificador que
la pasarela no encuentra.

## Evidencia

`E-022` — observado en la corrida e2e completa de PT-128, contra el stack real.

## Por qué importa

1. **Semántica de error invertida**: entrada inválida del cliente reportada como fallo del servidor.
2. **Contamina lo que miden D3 y D5**: `error_events` y cualquier alerta sobre 5xx registran fallos
   de servidor causados por el cliente.
3. **Fuga menor**: el mensaje nombra la URL del entorno de PayPal y la referencia.
4. **Ya se corrigió este mismo defecto en otro sitio.** PT-124 / F-41 se tituló *«un error del
   cliente no se registra como fallo del servidor»*. Aquí sobrevive, en la ruta de depósito.

## Por qué MEDIA y no más

No pierde dinero, no corrompe datos, no permite acreditar nada indebido: la petición **falla**, que
es lo correcto — falla mal, no falla peligrosamente. Exige sesión y está limitada a 10
peticiones/minuto.

Lo que sube el peso es dónde ocurre: la ruta de depósito de **P-005 WalletTransaction**, producto
CRÍTICO, y el efecto sobre las señales de fiabilidad.

```
impacto 2 (medio) × probabilidad 3 (probable) = riesgo 6 MEDIO
```

Probabilidad 3 porque cualquier referencia mal escrita lo dispara, y el reintento de un usuario
confundido es el caso normal, no el raro.

## Lo que este hallazgo NO afirma

- **No se probó con credenciales de producción.** Con credenciales válidas y una orden inexistente
  PayPal devolvería igualmente 404 y la cadena sería la misma, pero eso es razonamiento, no medición.
- **No se revisaron Mercado Pago ni Stripe.** Pueden tener el mismo hueco. Es lo primero que debería
  mirar quien lo corrija — y si lo tienen, la corrección es una sola, en el sitio donde se traduce
  el error de pasarela.
- No se intentó explotarlo.

## Corrección propuesta (no aplicada)

Traducir el fallo de la pasarela a un error de dominio antes de que salga: una referencia que la
pasarela no encuentra es un **404** o un **400**, no un 500. Y hacerlo donde valga para los tres
adaptadores, no sólo para PayPal.

## Estado

`ABIERTA`. Tipo `BUG`: `[R44]` reserva el cierre al humano. **Requiere su propio Proposal Gate**;
no entra en PT-127..PT-130.

## Revisión — S-002-R3 (2026-07-27): el hallazgo estaba mal encuadrado

Abierta por un reproche del humano: *«no estás consultando graphify, tampoco los documentos… desde
ayer se solucionó toda la parte de payments»*.

**Tenía razón, y la corrección es de fondo.**

### Lo que faltaba mirar

`docs-v2/4-ingenieria/Catalogo-de-API.md:51` documenta el flujo real de depósito:

```
POST /payments/initiate  ->  pasarela  ->  webhook / via garantizada  ->  acreditacion
```

Es el ciclo de pago de PT-080, con las garantías de PT-087 y los ADR-034 a ADR-040. **El depósito
sí se resolvió**: se resolvió sustituyendo el flujo entero.

### Lo que se comprobó ahora

`POST /api/v1/wallet/deposit` —el endpoint de este hallazgo— **no lo llama nadie**. Búsqueda sobre
todo `src/`:

```
src/api/test/e2e/wallet.e2e-spec.ts:80      .post('/wallet/deposit')     <- el UNICO llamante
```

Ni el CLIENT, ni el ADMIN, ni el BASE. Las referencias del CLIENT (`app.controller.ts:131`) son a
la **página** `/wallet/deposit`, no al endpoint del API. Y `/payments/initiate`, que es el camino
real, **funciona y su test pasa**.

### Qué cambia

`H-018` describe un defecto real —un error de la pasarela sale como 500 en vez de 4xx— sobre un
**endpoint legado que ningún cliente alcanza**.

```
severidad:     MEDIA (5)  ->  BAJA (1)
impacto:       2          ->  1     no lo alcanza ningun cliente de la plataforma
probabilidad:  3          ->  2     solo por llamada directa al API
riesgo:        6 MEDIO    ->  2 BAJO
```

**No se cierra ni se descarta**, por dos razones: el endpoint existe y responde, y la traducción de
errores de pasarela a errores de dominio sigue siendo la corrección correcta si algún día se
reactiva. Pero deja de ser trabajo prioritario.

### La pregunta que sustituye a este hallazgo

No es «cómo traduzco el error», es **«por qué sigue existiendo `/wallet/deposit`»**. Un endpoint sin
llamantes, superado por el ciclo de pago, con validación propia del importe contra la pasarela, es
superficie que nadie mantiene. Retirarlo o marcarlo como obsoleto es una **decisión de arquitectura**
y se lleva a `PENDIENTES`.

### Lo que yo hice mal, dicho

Diagnostiqué desde el sistema en marcha sin consultar antes `docs-v2/`, que es lo que FDGE exige
como fuente obligatoria. El síntoma era real; el encuadre, equivocado. Un endpoint sin llamantes no
es «la ruta de depósito de un producto CRÍTICO».
