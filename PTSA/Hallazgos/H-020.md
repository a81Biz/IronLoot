# H-020 — La página de Configuración del portal llama a una ruta que no existe

## Descripción

`src/apps/client/src/app.controller.ts:88` pide:

```ts
const settings = await apiGet(getToken(req), "/api/v1/users/settings");
```

Esa ruta **no existe**. `UsersController` expone `@Get('me/settings')` (línea 177) y
`@Patch('me/settings')` (línea 190). La petición cae en el comodín `@Get(':id')`, el
`ParseUUIDPipe` rechaza `settings` como identificador y devuelve **400**.

Comprobado con sesión real:

```
400  GET /api/v1/users/settings      -> {"code":"VALIDATION_ERROR","message":"Validation failed (uuid...)"}
200  GET /api/v1/users/me/settings   -> {"language":"es","notifications":{"email":true,"inApp":true}}
```

## Evidencia

`E-024`.

## Por qué D1 y no D2

El producto que falla es una **página que el usuario abre**: «Configuración» está en el menú del
portal (`layouts/client.html:57`). No es un defecto de integridad interna, es un producto del
dominio que no se entrega. `[A2]` — se audita el producto, no el componente.

## Por qué ALTA

```
impacto 3      una pagina del menu principal del portal privado no funciona
probabilidad 4 ocurre SIEMPRE, para todos los usuarios, en cada visita
riesgo = 12 CRITICO
```

No es CRITICA porque no toca dinero ni datos: la página no carga, no corrompe nada.

## Lo que agrava el caso

**El comodín `@Get(':id')` convierte un 404 honesto en un 400 confuso.** Si la ruta simplemente no
existiera, el error diría «no existe». En vez de eso dice «uuid inválido», que manda a quien lo
investigue a mirar el identificador — que no es el problema.

Es la misma clase de defecto que `CLAUDE.md` describe para la CSP: *«no funcionará y el navegador
no dirá nada»*. Aquí sí dice algo, pero dice lo que no es.

## Cómo apareció

Verificando la ruta de `settings` a raíz de H-019, y **después** de consultar `docs-v2` como
manda FDGE. No lo habría encontrado siguiendo sólo el rastro del código: hizo falta comparar lo que
el CLIENT pide con lo que el API expone.

## Lo que este hallazgo NO afirma

- **No se ha comprobado si otras páginas del CLIENT llaman a rutas inexistentes.** Es lo primero
  que hay que barrer, y probablemente merece una guarda: el contrato entre el SSR y el API no lo
  vigila nada hoy.
- No se ha medido desde cuándo está roto.

## Corrección propuesta

`/api/v1/users/settings` → `/api/v1/users/me/settings` en `app.controller.ts:88`.

Y lo que impide que vuelva: una guarda que compruebe que **toda ruta del API que el CLIENT invoca
existe en el API**. El repositorio ya tiene el patrón para este tipo de contrato
(`orden-de-scripts.spec.ts`, `plantillas-sin-js-inline.spec.ts`).

## Revisión — PT-132 (2026-07-28): CORREGIDA

**Estado: `ABIERTA` → `CORREGIDA`.** `[R44]`: lo cierra el humano.

`app.controller.ts:88`: `/api/v1/users/settings` → `/api/v1/users/me/settings`. Verificado en vivo:
la ruta vieja sigue devolviendo 400 (correcto, no existe) y la nueva devuelve 200.

### El mecanismo, que es lo que importa

`test/unit/web-views/rutas-que-el-client-invoca.spec.ts` comprueba que **toda ruta del API que el
CLIENT invoca existe en el API**. Nada vigilaba ese contrato.

Cubre **el SSR y el JavaScript de navegador**. Lo segundo no estaba en la primera versión y era la
mitad que faltaba: el depósito del portal llama a `/api/v1/payments/initiate` desde
`public/js/pages/pages-wallet-deposit.js`, no desde el controlador.

Tres decisiones, todas escritas en el fichero y con caso de control:

1. **Una ruta literal exige un destino literal.** Es lo que hace útil la guarda: `/users/settings`
   «casaba» con `@Get(':id')` a nivel de enrutado, y por eso el defecto era invisible.
2. **Los comentarios se descartan.** Sin esto, el comentario que explica cuál era la ruta rota hace
   fallar la guarda. Pasó de verdad — y le pasó lo mismo a la guarda del job de CI en PT-128.
3. **Un literal que acaba en `/` es un prefijo**, no una ruta: el JS concatena
   (`'/api/v1/payments/status/' + ref`). Tratarlo como ruta completa daba un falso positivo, y una
   guarda con falsos positivos acaba borrada.

### El barrido completo

Seis rutas invocadas desde el SSR, todas comprobadas con sesión real. **Una rota de seis.** Con el
JS de navegador incluido, la guarda vigila hoy todo el contrato CLIENT↔API.

### Lo que sigue sin cubrirse

**El ADMIN y el BASE no están en la guarda.** Sólo el CLIENT. Ampliarla es barato y queda anotado.
