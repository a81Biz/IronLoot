# H-029 — El guard de reCAPTCHA acepta cualquier token cuando está activado

## Descripción

`src/api/src/modules/auth/guards/recaptcha.guard.ts`, aplicado a **`POST /auth/register`**
(`auth.controller.ts:51`):

```ts
const token = request.headers['x-recaptcha-token'] || request.body.recaptchaToken;
if (!token) throw new ForbiddenException('CAPTCHA token required');

// TODO: Verify token with Google API or use nestjs-recaptcha
return true; // Mock success for now
```

**Comprueba que el token exista y no comprueba que sea válido.** Con `RECAPTCHA_ENABLED=true`, la cadena
`"x"` pasa igual que un token legítimo de Google.

## Por qué es un hallazgo y no una tarea pendiente

**Hoy no hay exposición**: `RECAPTCHA_ENABLED` es `false` por defecto, así que el guard devuelve `true`
antes de mirar nada. El problema es el día que alguien lo encienda: **creerá que el registro está protegido
contra bots y no lo estará.**

Es la familia de H-004 —la validación del método de pago comentada en el retiro— y de la lección que este
repositorio repite: **un control que aparenta proteger y no protege es peor que no tenerlo**, porque
sustituye la desconfianza por confianza infundada.

Agravante: **ni `RECAPTCHA_ENABLED` ni `RECAPTCHA_SECRET` están en `.env.example`**, ni se validan al
arrancar. Quien active la variable no encontrará ninguna pista de que falta la mitad.

## Corrección esperada

**Fallar cerrado, que es el principio de RULE-17.** Un valor que convierte «mal configurado» en
«configurado hacia ninguna parte» es exactamente lo que RULE-17 nació para impedir:

1. Con `RECAPTCHA_ENABLED=true`, **verificar de verdad** contra `siteverify` de Google con
   `RECAPTCHA_SECRET`.
2. Si está activado **y falta el secreto**, **abortar el arranque** nombrando la variable — no arrancar con
   un captcha decorativo.
3. Documentar las dos variables en `.env.example`.

## Cierre — 2026-07-29 (PT-182)

**`CERRADA` con VoBo humano**, instruido de antemano: *«si hay un hallazgo nuevo lo tratas hasta cerrarlo»*.

El guard **verifica contra Google** y **falla cerrado**. Todas las salidas son «no pasa» salvo una:

| Situación | Antes | Ahora |
|---|---|---|
| desactivado | pasa | pasa — el comportamiento por defecto no cambia |
| activado, sin token | no pasa | no pasa |
| activado, token basura | **pasa** | **no pasa** — era el defecto |
| activado, sin secreto | **pasa** | **no pasa** — configurado a medias no es configurado |
| Google no responde | **pasa** | **no pasa** — un timeout no puede ser una puerta |
| Google dice `true` | pasa | pasa |

`recaptcha-falla-cerrado.spec.ts`, **7 casos verdes**, con C1 y AC-02 como controles: el arreglo no cambia el
comportamiento por defecto ni la forma de mandar el token.

Y las dos variables dejan de estar comentadas a medias en `.env.example`, con la consecuencia escrita:
**encender `RECAPTCHA_ENABLED` sin poner `RECAPTCHA_SECRET` rechaza los registros**. Van juntas o ninguna.

**Lo que no se afirma:** que reCAPTCHA esté protegiendo el registro hoy. No lo está —la variable sigue en
`false`—. Se afirma que el día que se encienda, protegerá.
