# H-032 — El servicio de correo se come el fallo, y con él el reintento de la cola

## Descripción

`EmailService` captura cualquier error de envío **dentro** y no lo relanza:

```ts
} catch (error: any) {
  this.log.error('Failed to send verification email', { error: error.message, to } as any);
  // Don't rethrow to avoid breaking registration flow?
  // Ideally should queue or retry. For now log error.
}
```

Los dos métodos hacen lo mismo: `sendVerificationEmail` y `sendPasswordResetEmail`. **El fallo nunca llega a
quien llamó.** Hay `log.error`, así que no es un silencio — pero el flujo continúa como si el correo hubiera
salido, y eso rompe dos cosas distintas.

## Lo primero: acabo de afirmar algo que no era cierto

El cierre de **H-030** (PT-182, hace minutos) dice que el reenvío de verificación *«propaga el fallo — un
`catch` que se lo comiera reproduciría el defecto por otra vía»*. **La mitad de esa frase es falsa.** El
`catch` existe: está una capa más abajo, dentro de `EmailService`.

Y el caso C2 de `reenvio-de-verificacion.spec.ts` —«si el envío FALLA, no se responde éxito»— pasa porque el
doble de prueba rechaza. **En producción no puede rechazar.** Es un caso verde que comprueba un escenario
imposible, exactamente el mismo defecto que ya corregí en AC-01 de esa misma guarda unas horas antes.

Lo que H-030 dejó realmente arreglado —que el correo **sale**— sigue siendo cierto y está comprobado en vivo
(`1 → 2` en Mailhog). Lo que no está arreglado es el camino del fallo.

## Lo segundo, y es peor: el reintento de la cola no puede ocurrir

`notification-queue.worker.ts` está escrito para reintentar:

```ts
try {
  await this.emailService.sendVerificationEmail(to, context['token'] as string);
} catch (err) {
  this.logger.error(`Email job ${job.id} failed (attempt ${job.attemptsMade + 1})`, err);
  throw err;   // ← para que BullMQ lo reintente
}
```

Cuenta intentos, registra el número y **relanza para que la cola reintente**. Ese `catch` **no puede
ejecutarse nunca**: lo que llama por debajo no lanza. Un envío fallido marca el trabajo como **completado con
éxito** y el reintento —el mecanismo de recuperación— no existe.

Es la familia de **H-014**, **H-015** y **H-027**, y este repositorio ya la tiene escrita como principio: *un
mecanismo que no se ejecuta no avisa de nada.* Aquí hay tres capas de recuperación —el `catch` del worker, el
contador de intentos, la política de reintentos de BullMQ— y ninguna llega a activarse porque la de abajo
absorbe la excepción.

## Impacto

- **El reenvío de verificación responde «revisa tu bandeja» cuando el envío ha fallado.** Es el mismo síntoma
  que H-030, por otra vía: distinto código, misma mentira al usuario.
- **La cola no reintenta.** Un fallo transitorio del SMTP —el caso para el que la cola existe— se pierde en
  vez de repetirse.
- **La recuperación de contraseña queda sin rastro para el usuario**: se le dice que recibirá un enlace y no
  llega ninguno.

## Corrección esperada

**El servicio de correo no decide por sus llamantes.** `sendVerificationEmail` y `sendPasswordResetEmail`
propagan, y **cada llamante declara qué hace con el fallo**, porque la respuesta correcta es distinta en cada
uno:

| Llamante | Qué debe hacer | Por qué |
|---|---|---|
| **Reenvío de verificación** | **propagar** | Es lo único que hace el endpoint. Si no salió, no puede responder que salió |
| **Cola** (`notification-queue.worker`) | **propagar** | Su `catch` y su contador de intentos existen para esto |
| **Registro** | **capturar y registrar** | La cuenta ya está creada; tumbar el registro por un SMTP caído sería peor, y ahora hay una vía de reenvío que funciona |
| **Recuperación de contraseña** | **capturar y registrar** | La respuesta es **opaca a propósito** para no revelar si la dirección existe. Propagar convertiría una caída del SMTP en un **oráculo de enumeración**: 500 para las direcciones que existen, 200 para las que no |

Las dos capturas van **con su motivo escrito**. Una captura razonada no es el defecto; el defecto es la
captura que decide en nombre de todos.

| Llamante | Que hace | Motivo escrito en el codigo |
|---|---|---|
| Reenvio de verificacion | **propaga** | Es lo unico que hace el endpoint |
