# H-025 — `cross_coherence_verified = verificado` sobre una base con cero filas

## Descripción

`npm run audit:domain` cierra su Nivel 3 (coherencia inter-producto) así, ejecutado hoy dentro del
contenedor:

```
  [OK  ] P-002 → P-003    El importe del pedido coincide con el precio final  (0)
  [OK  ] P-003 → P-010    La comision es el porcentaje aplicado al importe  (0)
  [OK  ] P-010 → P-009    El registro de comision coincide con el asiento FEE_PLATFORM  (0)
  [OK  ] P-003 → P-006    Toda disputa cuelga de un pedido existente  (0)
  [OK  ] P-002 → P-007    El tipo del aviso corresponde al evento  (0)

  cross_coherence_verified = verificado
  5 de 5 medidas · 0 incoherente(s) · 0 sin poder mirar
```

**Y la base tiene cero pedidos, cero pagos, cero comisiones y cero asientos** (`E-030`).

Las cinco consultas se ejecutaron sin error y devolvieron «0 incoherencias» **porque no había una sola
fila que comparar**. El veredicto no distingue *«comparé y cuadra»* de *«no había nada que comparar»*.

## Por qué es ALTA, y por qué no es «la limitación conocida de la base vacía»

Porque **el propio código declara la protección que no implementa**. El docstring de
`veredictoCoherencia()` dice, literalmente:

> *«Un catalogo vacio da `sin_datos`, no `verificado`: afirmar que se verifico la coherencia de cero
> pares es la version degenerada del mismo error.»*

Y `domain-rules.ts:383` sólo trata como `sin_datos` el caso `medidas === 0`, que es «todas devolvieron
`ERR`». Una consulta que corre limpiamente sobre cero filas cuenta como **medida**:

```ts
const noMedidas = comprobaciones.filter((c) => c.resultado === 'ERR').length;
const medidas = comprobaciones.length - noMedidas;
const estado = incoherentes > 0 ? 'incoherente'
             : medidas === 0 || noMedidas > 0 ? 'sin_datos'
             : 'verificado';
```

No hay denominador. `resultado` es el número de filas **incoherentes**; nadie cuenta las filas
**comparadas**.

**Es H-021 con otra ropa, y es la sexta aparición del patrón de la casa.** H-021 era el mismo veredicto
diciendo `true` con las cinco en error; PT-149 lo arregló para el caso «no pude conectar» y **dejó el
caso «no había datos»**. Corregir el caso y no la clase es literalmente lo que a PT-129 le costó dos
repeticiones, y lo que H-014 hizo volver en cuatro días.

Y el contraste está en el mismo fichero, veinte líneas más arriba: `rubric_compliance_score` **sí**
declara su denominador y enumera las trece reglas que quedaron fuera. Alguien pensó este problema para el
score y no lo trasladó —otra vez— a la línea de al lado.

## Impacto

Las cinco comprobaciones cubren **dinero**: importe del pedido contra precio final, comisión contra
importe, registro de comisión contra el asiento `FEE_PLATFORM`. Un delta sync que lea `verificado`
concluye que el dinero es coherente **sin que se haya comparado un solo peso**.

Y no es hipotético: **es lo que este delta sync habría concluido** si no se hubiera cruzado la línea con
el conteo de filas de `E-030`. `[A1]` —evidencia sobre opinión— es exactamente lo que queda anulado.

Agravante de oportunidad: cuanto **más vacía** está la base, más verde sale. Que es la propiedad inversa
de la que debe tener un instrumento de auditoría.

## Corrección esperada

Cada comprobación devuelve **dos números**: filas comparadas y filas incoherentes. El veredicto se
deriva de los dos:

- `verificado` — las cinco compararon **al menos una fila** y ninguna falló.
- `incoherente` — alguna comparación falló.
- `sin_datos` — alguna no pudo mirar (`ERR`) **o comparó cero filas**.

Y el proceso **no sale con 0** cuando no pudo medir, igual que ya hace para `ERR` desde PT-149.

Corolario, por si sirve para la próxima: el patrón se ha repetido seis veces. Lo que distingue a un
instrumento de auditoría de un test es que **tiene que declarar su denominador**.
