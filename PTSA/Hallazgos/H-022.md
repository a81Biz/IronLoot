# H-022 — Los dos checkpoints de delta sync no pueden ejecutarse donde vive npm

## Descripción

`audit:domain` (D1.N1) y `audit:reliability` (D5) consultan la base con
`execSync('docker exec ironloot-db psql …')`:

```
src/api/scripts/domain-rules.ts:268
src/api/scripts/reliability-check.ts:55
```

Dentro del contenedor del API **no hay binario `docker`**, así que los dos fallan con
`/bin/sh: 1: docker: not found`. Desde el host funcionan.

## Por qué importa, si desde el host funcionan

Porque **PT-138 (F-135-B) corrigió exactamente esto** en el tercer script: pasó
`observability-check.ts` de `docker exec psql` a `PrismaClient.$queryRawUnsafe` precisamente porque
un checkpoint tiene que correr donde corre npm. Se arregló uno de los tres y **los otros dos se
quedaron con la forma vieja**, sin que nada lo notara.

Es el mismo patrón que ADR-048 describe para los locks: *una regla que dice lo contrario de lo que el
repositorio hace es una trampa para quien la lea y la respete.* Quien siga la convención de CLAUDE.md
—«npm no se ejecuta en el host: se ejecuta en el contenedor»— obtiene `SIN_DATOS` de los dos
checkpoints y ninguna pista de por qué.

Agravante: **los dos salen con código 0**. Un fallo que sale con 0 no es un fallo para nadie que lo
automatice.

## Corrección esperada

Consultar con `PrismaClient`, como ya hace `observability-check.ts`. La conexión sale de
`DATABASE_URL`, que ambos entornos tienen. Y salir distinto de 0 cuando no se pudo medir.

`ABIERTA`. No lo cierra el agente.
