# H-042 — Un webhook de PayPal con firma fabricada obtuvo `SIGNATURE_OK` y llegó a intentar la captura

## Qué se observó, ejecutando

`QA-PP-15` («Un webhook fabricado se rechaza con 401») falló con **HTTP 400** en las tres corridas de la
suite del 2026-07-31. Reproducido a mano contra el API en pie:

```
POST /api/v1/payments/webhook/PAYPAL
  paypal-auth-algo:          SHA256withRSA
  paypal-cert-url:           https://api.sandbox.paypal.com/cert.pem
  paypal-transmission-id:    falso-1
  paypal-transmission-time:  2026-08-01T00:00:00Z
  paypal-transmission-sig:   ZmFsc2E=          ← «falsa» en base64
  body: { id: WH-FALSO, event_type: CHECKOUT.ORDER.APPROVED, resource: { id: X } }

→ 400
```

Y la secuencia del log del API, en este orden:

```
info   Received PayPal webhook CHECKOUT.ORDER.APPROVED (WH-FALSO)
info   Capturing PayPal order X                    ← YA ESTÁ CAPTURANDO
warn   PayPal respondio 404 · httpStatus 400       ← sólo falla porque el pedido no existe
```

La traza lo confirma desde la otra punta:

```sql
SELECT step, outcome FROM payment_cycle_events ORDER BY id DESC LIMIT 3;
 NOTIFICATION_RECEIVED | OK
 SIGNATURE_OK          | OK      ←  sobre una firma fabricada
```

## Por qué importa

**Lo único que detuvo el flujo fue que el identificador de pedido no existía en PayPal.** La barrera que
debía detenerlo —`RN-50`: *«validar la firma antes de procesar»*— **dijo que la firma era buena**.

Y el registro afirma `SIGNATURE_OK`, que es peor que un fallo: quien audite ese ciclo después leerá que
la firma se verificó y fue correcta.

## Lo que NO está determinado, y por eso esto es una investigación

`verifyWebhookSignature` **sí se llama antes de `captureOrder`** —comprobado en
`paypal.provider.ts:470`— y **sí consulta** `/v1/notifications/verify-webhook-signature`. El código hace
lo que dice. Lo que falta por medir es **por qué esa consulta devolvió `SUCCESS`**:

- ¿el endpoint de **sandbox** de PayPal es permisivo con firmas inválidas?
- ¿el cuerpo que se le envía no es el que espera, y responde `SUCCESS` por omisión?
- ¿`PAYPAL_WEBHOOK_ID` (`79912641J8336873F`) corresponde a otro webhook, y la verificación no aplica?

**No se toca el código sin saberlo.** Es el camino por el que entra dinero, y un parche a ciegas sobre
una verificación de firma puede cerrar la puerta buena y dejar abierta la mala.

## Alcance de la afirmación

Medido **en sandbox**. No está demostrado que ocurra igual en producción con credenciales reales, y
tampoco lo contrario. La probabilidad se fija en **2** por esa incertidumbre, no por confianza.

Lo que sí está demostrado sin depender del entorno: **el sistema afirma `SIGNATURE_OK` sobre una firma
que él mismo no verificó como buena**, y el rechazo llega por un 404 ajeno en vez de por la comprobación
que existe para eso.

## Procedencia

**No lo introdujo la tanda `PT-204`…`PT-233`**: `git diff master -- src/api/src/modules/payments/` está
vacío. Apareció al ejecutar la suite de navegador, que es el paso que llevaba pendiente desde antes de
esta tanda — y por el que nadie lo había visto.
