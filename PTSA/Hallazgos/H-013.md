# H-013 — La subida de imágenes deja elegir al cliente la extensión con la que se guarda el fichero

## Descripción

El endpoint `POST /api/v1/upload/image` acepta un fichero, valida que sea una imagen y lo guarda en
`uploads/`, que `ServeStaticModule` publica en `/uploads`. **Las dos comprobaciones que hace miran
campos que escribe el cliente, y la extensión con la que guarda también.**

```ts
// upload.controller.ts:53 — file.mimetype es un campo del multipart, lo escribe el cliente
if (!file.mimetype.match(/^image\/(jpg|jpeg|png|gif|webp)$/)) { ... }

// upload.service.ts:19 — file.originalname tambien
const fileName = `${uuidv4()}${extname(file.originalname)}`;
```

Un fichero enviado con `Content-Type: image/png` (pasa la validación) y nombre `x.html` se guarda
como `<uuid>.html`. E-016 mide que el servidor lo devuelve con `Content-Type: text/html`.

## Por qué `nosniff` no lo cubre

Helmet pone `X-Content-Type-Options: nosniff` y **funciona**. Esa cabecera impide que el navegador
adivine un tipo distinto del declarado; aquí el declarado ya es `text/html`. No hay nada que
adivinar. Es la clase de mitigación que se lee en un checklist como presente y no aplica al caso.

## Alcance

`COOKIE_DOMAIN=.ironloot.local` — el punto inicial envía la cookie de sesión a todos los
subdominios, `api.ironloot.local` entre ellos. Script ejecutándose en el origen del API está dentro
del alcance de la cookie de sesión.

Mitigación real existente: **el endpoint exige sesión** (`@UseGuards(JwtAuthGuard)`). No es anónimo.
Por eso es ALTA y no CRÍTICA: hace falta una cuenta, y el registro exige verificar el correo.

## Segundo defecto, misma línea

`@UseInterceptors(FileInterceptor('file'))` **no declara `limits`**. El almacenamiento por defecto de
Nest es en memoria: el fichero entero se acumula en RAM antes de que el controlador llegue a
validarlo. La validación de tipo ocurre *después* de haber recibido el fichero completo.

## Relación con TD-015

PT-123 lo encontró de lado mientras medía la alcanzabilidad del aviso de `multer`. **Es más grave
que el aviso**: el de `multer` exige una migración de plataforma y es un agotamiento de recursos;
este se arregla sin subir nada y es ejecución de script en el origen del API.

Confirma la tesis de PT-123: la severidad hay que medirla, no heredarla. Aquí el número de
`npm audit` señalaba al vecino del problema.

## Corrección requerida

1. Derivar la extensión del **contenido verificado**, nunca de `originalname`.
2. Verificar los **bytes de cabecera** del fichero, no el `mimetype` declarado.
3. `limits.fileSize` en el interceptor, para rechazar antes de acumular.
4. `.svg` fuera: es un tipo `image/*` que ejecuta script en navegación directa.

## Regla que viola

`RN-SEC`: ningún dato bajo control del cliente decide dónde ni cómo se persiste algo.


## Revision — 2026-07-27 (PT-124)

**ABIERTA -> CORREGIDA.** No se cierra: es un BUG y el agente no cierra bugs.

`file-signature.ts` decide el tipo por los **bytes de cabecera**. La extension sale de ahi y
`originalname` se recibe solo para no usarlo. `FileInterceptor` lleva `limits.fileSize` (5 MB) —en
el interceptor, no en el controlador: el almacenamiento por defecto es en memoria, y validar el
tamaño en el handler seria mirar la factura despues de pagarla.

**No se uso `file-type`**, que ya estaba en el arbol y hace esto mismo: tenia un aviso abierto que
PT-123 clasifico como inalcanzable *precisamente porque aqui solo se suben imagenes*. Llamarlo desde
este punto lo habria vuelto alcanzable. Cuatro formatos, firmas de longitud fija, cero parsing.
