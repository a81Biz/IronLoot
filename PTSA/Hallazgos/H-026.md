# H-026 — El endpoint de diagnóstico dice «degraded» siempre, y una caída de Redis diría lo mismo

## Descripción

`GET /api/v1/health/detailed`, en vivo:

```json
{
  "status": "degraded",
  "dependencies": {
    "database": { "status": "up", "latency": 0 },
    "redis":    { "status": "unknown", "message": "Redis check not implemented" }
  }
}
```

Son dos líneas de `health.service.ts`:

```ts
// :89
return { status: 'unknown', message: 'Redis check not implemented' };

// :65
status: anyDown ? 'unhealthy' : allUp ? 'healthy' : 'degraded',
```

`redis` **nunca** puede valer `up`, así que `allUp` **nunca** es cierto: el endpoint **no puede** devolver
`healthy`. Ningún estado del sistema lo produce.

## Las dos consecuencias, y la segunda es la que importa

**1. Reporta un problema que no existe, en cada consulta.** Es ruido que enseña a descartar la fuente —
el mismo mecanismo que PT-159, PT-166 y PT-172 vinieron a quitar de la salida de la suite. Quien se
acostumbra a ver `degraded` deja de mirarlo.

**2. Y si Redis se cayera de verdad, diría exactamente lo mismo.** El estado seguiría siendo `unknown`,
el agregado seguiría siendo `degraded`. **Una caída real de Redis es indistinguible del funcionamiento
normal** en el único endpoint que existe para diagnosticarla.

Esa segunda es la que lo hace un hallazgo D3 y no una tarea pendiente: no es que falte una comprobación,
es que **su ausencia está indistinguible de su fallo**.

## Por qué pesa en este sistema

`REDIS_URL` es el **único contrato de Redis** (PT-137) y de él dependen **las colas, el rate limiting, el
cerrojo distribuido y las sesiones de ADMIN**. Perder Redis en caliente degrada las cuatro cosas.

Este repositorio ya pagó por no poder ver Redis: RULE-17 existe porque un valor por defecto convertía
«mal configurado» en «configurado hacia ninguna parte», y el síntoma era *«Nest application successfully
started»* seguido de un 500 sobre `maxRetriesPerRequest` **que no menciona Redis**. La lección se aplicó
al **arranque** —el proceso aborta si falta la variable— y la degradación **en caliente** quedó sin
cubrir. Es el mismo hueco, un estado más tarde.

## Por qué MEDIA y no ALTA

Porque **nada depende del endpoint roto**:

- El `healthcheck` de Docker apunta a `/api/v1/health` (`docker-compose.yml:192`), que devuelve `200` y
  `healthy`. Ningún contenedor cae por esto.
- `database` **sí** se comprueba de verdad, con latencia medida.
- El arranque está protegido por la validación de `REDIS_URL`.

El sistema está sano; lo que no se puede **observar** es Redis. Impacto 2. Probabilidad 4: es
determinista — sale en cada consulta, hoy y siempre.

## Corrección esperada

Implementar la comprobación con el cliente que ya existe (`RedisService` / el que usa
`distributed-lock.service.ts`): un `PING` con timeout corto, `up` con su latencia o `down` con el error.
Con eso, `allUp` vuelve a ser alcanzable y `degraded` recupera su significado.

**Y decidir explícitamente qué es una dependencia no comprobable**, porque hoy `unknown` se mezcla con
`degraded` y son cosas distintas: «no lo sé» no es «está mal». Es la misma distinción de tres estados que
PT-138 introdujo para D3 y PT-149 para el veredicto de coherencia.
