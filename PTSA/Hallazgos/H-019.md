# H-019 — Un `PATCH` parcial de ajustes borra los ajustes que no envías

## Descripción

`PATCH /api/v1/users/me/settings` con un payload parcial **destruye las ramas que no se envían**.
Observado en vivo, contra el sistema en marcha:

```
ANTES   {"language": "es", "notifications": {"email": true, "inApp": true}}
PATCH   {"language": "en"}
DESPUES {"language": "en"}                    <- notifications borrado
```

## Causa

`users.service.ts:493` mezcla con `deepMerge(currentSettings, dto)`, y `deepMerge` recorre
`Object.keys(source)`.

`dto` **no es un objeto plano**: `main.ts:84` configura el `ValidationPipe` con `transform: true`,
así que llega una instancia de `UserSettingsDto` con **todas** las propiedades declaradas como
claves propias — las ausentes, con valor `undefined`.

```
Object.keys(dto) -> ['language', 'notifications']
                                   ↑ presente, undefined
isObject(undefined) === false  ->  output.notifications = undefined
```

**`deepMerge` está bien escrito.** Lo que le llega ya viene contaminado.

## Evidencia

`E-023` — el antes y el después contra el API en marcha, más la lectura del código.

## Por qué ALTA

Es **pérdida silenciosa de datos del usuario**. La petición devuelve 200 y nadie se entera hasta que
los avisos dejan de llegar — y `notifications` gobierna exactamente eso: si el usuario recibe
correos y avisos in-app. En una plataforma de subastas, es perderse que te han superado la puja.

```
impacto 3 (alto: pierde datos del usuario, en silencio)
probabilidad 4 (frecuente: CUALQUIER PATCH parcial lo dispara, que es el uso normal de un PATCH)
riesgo = 12 CRITICO
```

No es CRITICA porque no toca dinero ni compromete la seguridad: se pierde configuración, no saldo.

## Cómo apareció

Corrigiendo los specs e2e de PT-131. `settings.e2e-spec.ts` seguía fallando después de arreglar
todas las capas de contrato viejo, y afirmaba algo razonable: que cambiar el idioma no debe tocar
las notificaciones.

**El test llevaba meses teniendo razón y nadie lo escuchaba**, porque el job de CI que lo habría
ejecutado no podía terminar (H-015). Es el mejor argumento a favor de arreglar el pipeline.

## Lo que este hallazgo NO afirma

- **No se ha revisado si otros `PATCH` tienen el mismo patrón.** Es lo primero que debería mirar
  quien lo corrija: cualquier servicio que mezcle un DTO transformado contra un JSON almacenado
  tiene el mismo agujero. Podría no ser un defecto sino una **familia**.
- No se ha medido el impacto en usuarios reales: la base de desarrollo tiene 4 usuarios.

## Corrección propuesta (no aplicada)

Descartar las claves con valor `undefined` antes de mezclar — en `deepMerge`, que es donde vale para
todos los llamantes:

```ts
Object.keys(source).forEach((key) => {
  if (source[key] === undefined) return;   // no enviado != enviado como vacio
  ...
});
```

Y una prueba que fije el contrato: `PATCH` parcial conserva las ramas hermanas. El e2e que lo
detectó ya existe; lo que falta es que corra.

**Ojo con `null`**: hay que decidir si `null` significa «bórralo» o se ignora igual. Hoy el DTO no
lo permite, pero la decisión conviene escribirla.
